# Інформаційна система обліку витрат на харчування

REST API для обліку витрат на їжу: покупки, категорії, підсумки за
календарні періоди, розбивка за категоріями, дані графіків, місячні бюджети,
експорт у CSV і резервна копія бази.

Індивідуальний проєкт практикуму з дисципліни «Проєктування інформаційних
систем», варіант 3. Виконав: Майстренко Ілля Ігорович, група КН-32, КПІ ім.
Ігоря Сікорського, ННІ прикладного системного аналізу, кафедра системного
проектування.

Версія 1.1.0: базова специфікація плюс адендум ADD-01 (бюджети).

## Що це таке

Система відповідає на питання «скільки насправді йде грошей на їжу» і не дає
дізнатися про це в кінці місяця. Облік ведеться в гривнях, у часовому поясі
`Europe/Kyiv`.

Поточна версія — серверна: REST API без графічного інтерфейсу. Вимоги рівня
інтерфейсу користувача свідомо залишені поза обсягом і перелічені в
`docs/requirement-coverage.md`.

## Вимоги до середовища

| Що | Версія | Навіщо |
|---|---|---|
| Python | 3.13 або новіший | код використовує запис типів `X \| None` без імпорту |
| Операційна система | Windows, Linux, macOS | залежностей від ОС немає |

Зовнішня база даних не потрібна: використовується SQLite, файл створюється
сам при першому запуску.

## Встановлення

```
git clone https://github.com/d1aboli/food-expenses-is.git
cd food-expenses-is

python -m venv .venv
```

Активація віртуального середовища:

```
.venv\Scripts\activate          # Windows PowerShell
source .venv/bin/activate       # Linux, macOS
```

Встановлення залежностей:

```
python -m pip install -r requirements.txt
```

Для перевірки оформлення коду й збірки документації потрібен ще один набір:

```
python -m pip install -r requirements-dev.txt
```

Про `tzdata` в `requirements.txt`: під Windows системної бази часових поясів
немає, і без цього пакета запуск падає з `ZoneInfoNotFoundError` на поясі
`Europe/Kyiv`. На Linux пакет зайвий, але не заважає.

## Запуск

```
python run_server.py
```

Сервер слухає `http://127.0.0.1:8080`. Базова адреса API —
`http://127.0.0.1:8080/api/v1`, як указано в розділі `servers` контракту.

Інтерактивна сторінка з переліком усіх операцій, де запит можна одразу
виконати: `http://127.0.0.1:8080/docs`.

Перевірити, що сервер піднявся:

```
curl http://127.0.0.1:8080/api/v1/profiles
```

Відповідь на порожній базі — `{"items":[]}`.

З чого почати роботу, які запити надсилати далі — у документації
користувача `docs/user-guide.md`.

## Конфігурація

Налаштувань небагато, і всі задаються змінними середовища. Кожна незалежна:
можна змінити лише каталог копій, не чіпаючи решти.

| Змінна | Типове значення | Що задає |
|---|---|---|
| `FOOD_EXPENSES_DB` | `data/food-expenses.db` | файл бази даних |
| `FOOD_EXPENSES_LOG_DIR` | `logs/` | каталог журналів |
| `FOOD_EXPENSES_BACKUP_DIR` | `data/backups/` | каталог резервних копій |

Приклад запуску з окремою базою:

```
set FOOD_EXPENSES_DB=D:\data\test.db    # Windows
export FOOD_EXPENSES_DB=/tmp/test.db    # Linux, macOS
python run_server.py
```

Каталоги створюються самі при старті. Схема бази доводиться до останньої
версії теж при старті, окремої команди міграції немає.

Порт і адресу можна змінити аргументами:

```
python run_server.py --port 9000
python run_server.py --host 0.0.0.0 --port 9000
```

За замовчуванням сервер слухає саме `127.0.0.1`, а не `0.0.0.0`: система
працює з особистими витратами, і виставляти її в мережу без потреби не слід.

## Журнали

| Файл | Що містить |
|---|---|
| `logs/app.log` | усі дії системи: створення, зміна, видалення записів, відхилені запити |
| `logs/errors.log` | лише помилки виконання |
| `logs/test-runs.md` | історія прогонів тестів |

Кожен запит має власний ідентифікатор, який стоїть у кожному рядку журналу
цього запиту і повертається клієнту заголовком `X-Trace-Id`. За ним зручно
знайти в журналі все, що сталося під час конкретного запиту.

Перші два файли до репозиторію не потрапляють.

## Тести

```
python tools/run_tests.py
```

162 тести. Скрипт запускає `pytest` і дописує рядок у `logs/test-runs.md` із
кількістю успішних і неуспішних.

Якщо журнал прогонів не потрібен, можна і просто:

```
python -m pytest
```

## Перевірки

Усі команди запускаються з кореня репозиторію.

| Команда | Що перевіряє |
|---|---|
| `python -m ruff check .` | відповідність коду конвенції `docs/coding-convention.md` |
| `python tools/check_reformat_safety.py` | чи змінює автоматичне переформатування поведінку програми |
| `python tools/check_docstrings.py` | повноту docstring-ів за `docs/docstring-tags.md` |
| `python tools/check_contract.py` | відповідність реалізації контракту `spec/api/openapi.yaml` |
| `python tools/requirement_coverage.py` | покриття вимог специфікації тестами |
| `python tools/check_docs.py` | відповідність документації фактичному коду |
| `python tools/audit_traceability.py` | повноту матриці простежуваності |

Усі сім мають завершуватися без зауважень.

## Документація

```
python -m sphinx -b html docs/sphinx docs/sphinx/_build/html
```

Результат — `docs/sphinx/_build/html/index.html`. Довідник збирається з
docstring-ів початкового коду; написаних окремо описів у ньому немає. Зібраний
одним файлом варіант лежить у репозиторії: `docs/api-reference.pdf`.

| Документ | Про що |
|---|---|
| `docs/user-guide.md` | документація користувача: сценарії роботи через API |
| `docs/api-reference.pdf` | технічний довідник за модулями й функціями |
| `docs/coding-convention.md` | конвенція оформлення коду |
| `docs/docstring-tags.md` | система теглів документації коду |
| `spec/srs.tex` | специфікація вимог |
| `spec/addendum-01-budgets.md` | адендум ADD-01: місячні бюджети |
| `spec/api/openapi.yaml` | затверджений контракт REST API |
| `spec/glossary.md` | глосарій предметної області |
| `spec/traceability.md` | матриця простежуваності |

## Структура репозиторію

```
src/food_expenses/      реалізація
  api/                  маршрути, схеми, обробка помилок
  services/             правила предметної області
  repositories/         доступ до бази
  money, periods,       обчислення й перевірка даних
  validation, text
  config, db,           інфраструктура
  logging_setup
tests/                  162 тести
tools/                  інструменти перевірки
spec/                   специфікація, контракт, адендум, глосарій
docs/                   документація
logs/                   журнали рішень і прогонів
```

Межа між шарами однобічна: шар знає лише про той, що під ним. Маршрут не
торкається SQL, служба не знає про HTTP, репозиторій не знає, яку вимогу він
обслуговує.

## Розробка

Проєкт виконано за Specification-Driven Development: спочатку специфікація,
потім контракт, потім тести, і лише тоді код. Історія Git відображає цей
порядок — для кожної групи вимог коміт `test:` передує коміту `feat:`.

Поведінка поза межами затвердженої специфікації вводиться адендумом, а не
правкою специфікації. Так додано бюджети: `spec/addendum-01-budgets.md`.

Рішення в контрольних точках і причини, з яких вони ухвалені, лежать у
`logs/`.
