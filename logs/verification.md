# Верифікація реалізації

Крок 7 лабораторної роботи №5, перша половина. Верифікація відповідає на
питання «чи зроблено систему правильно»: чи відповідає реалізація тому, що
записано в затверджених артефактах.

Друга половина — валідація — відповідає на інше питання, «чи зроблено ту
систему», і виконується людиною (`logs/validation.md`).

## Проти чого звірялася реалізація

| Артефакт | Версія |
|---|---|
| `spec/srs.tex` | 1.0, затверджена на SPEC-GATE |
| `spec/api/openapi.yaml` | 1.1.0, затверджений на API-GATE і оновлений адендумом |
| `spec/addendum-01-budgets.md` | ADD-01, затверджений на SPEC-ADDENDUM-GATE |

## 1. Покриття вимог тестами (REQ-NF-002)

Команда: `python tools/requirement_coverage.py`

| Показник | Кількість |
|---|---|
| Вимог оголошено | 64 |
| Покрито автоматизованими тестами | 50 |
| Перевіряються процесом, а не тестом | 9 |
| Поза обсягом ЛР5 | 5 |
| **Без покриття** | **0** |

Повний звіт із переліком тестів для кожної вимоги —
`docs/requirement-coverage.md`.

**Вимоги процесу** (REQ-NF-001, 002, 003, 004, 006, 007, 011, 013, 015)
перевіряються не тестом, а історією Git і записами в `/logs`. Тест не може
довести, що коміт `test:` був раніше за коміт `feat:` — це доводить історія
репозиторію.

**Поза обсягом ЛР5**: REQ-I-001, REQ-I-002, REQ-I-004, REQ-NF-012,
REQ-NF-014. Усі п'ять належать до інтерфейсу користувача. Завдання ЛР5 —
серверна реалізація REST API, тому вони свідомо не реалізовані, а не забуті.

## 2. Відповідність контракту

Команда: `python tools/check_contract.py`

```
spec/api/openapi.yaml: опис OpenAPI коректний
Операцій у контракті: 22
Реалізовано операцій:  22
Результат: реалізація повністю відповідає затвердженому контракту
```

Перевірка двостороння: немає ані операції контракту без реалізації, ані
операції в застосунку поза контрактом. Друге важливіше: саме так виявляється
поведінка, додана під час написання коду без зміни специфікації.

Окрім переліку операцій, форма кожної відповіді звіряється зі схемою з
контракту безпосередньо в тестах (`tests/contract.py`): тест бере схему з
`spec/api/openapi.yaml`, а не переписує її своїми словами.

## 3. Відповідність адендуму

Усі дев'ять вимог REQ-A-001..REQ-A-009 покриті тестами
(`tests/test_budgets.py`, 22 тести). Межі адендуму дотримані: операцій поза
переліком ADD-01 не з'явилося, бюджет на профіль у цілому й бюджет на
довільний період не реалізовані, заборони витрачати понад бюджет немає.

## 4. Прогін тестів

```
усього 162, успішних 162, неуспішних 0
```

Журнал прогонів — `logs/test-runs.md` (REQ-NF-005).

## 5. Журналювання

| Вимога | Стан |
|---|---|
| Усі дії системи в журналі | виконано: `app.log` містить події створення, зміни, видалення, експорту, резервної копії та кожен оброблений запит із trace-ID |
| REQ-NF-008, помилки окремо | виконано: `errors.log` наповнюється лише записами рівня помилки |
| Прив'язка журналу до запиту | виконано: trace-ID повертається клієнту в заголовку `X-Trace-Id` |

## 6. Статичний аналіз

`ruff` із наборами F, E, I по каталогах `src`, `tests`, `tools` — зауважень
немає. Прогін тестів із `-W error::SyntaxWarning` — попереджень немає.

## Знайдені розбіжності

Верифікація не знайшла розбіжностей між реалізацією і затвердженими
артефактами. Знайдені розбіжності **між самими артефактами** лишаються
відкритими питаннями:

| ID | Розбіжність | Стан |
|---|---|---|
| ВП-01 | Чи потрібне видалення профілю разом із даними | з ЛР2, операції немає в контракті, не реалізовано |
| ВП-02 | Контракт не описує тіла відповіді для непередбаченої помилки сервера | відкрите; такі помилки лише пишуться в журнал |
| ВП-03 | REQ-F-017 дозволяє ціле число, схема `Money` вимагає два знаки після коми | відкрите; API діє за контрактом |
| ВП-04 | Чи потрібні різні суми бюджету для різних місяців | відкрите, з адендуму ADD-01 |
| ВП-05 | Чи має сенс бюджет для службової категорії «Інше» | відкрите, з адендуму ADD-01 |

Окремо зафіксовано суперечність між критеріями прийняття REQ-F-031 і
REQ-F-033 щодо порожнього графіка. Вона розв'язана тлумаченням, записаним у
`logs/test-gate.md` і закріпленим тестом: точок стільки, скільки днів у
місяці, а «порожній графік» означає, що жоден стовпчик не піднімається над
нулем. До наступної редакції SRS це тлумачення має потрапити в текст вимоги.

## Висновок верифікації

Реалізація відповідає базовій специфікації, затвердженому контракту версії
1.1.0 та адендуму ADD-01. Прогалин у покритті вимог тестами немає. Поведінки
поза затвердженими артефактами не виявлено.
