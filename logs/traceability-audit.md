# Завершення матриці простежуваності та її аудит

Кроки 11 і 12 лабораторної роботи №6. Звіт інструмента —
`docs/traceability-audit.md`; цей журнал пояснює, що було дороблено й що
знайшов аудит.

Виконав: Майстренко Ілля, група КН-32. Дата: 16.11.2026.

## Що бракувало в матриці

Після ЛР5 матриця вела ланцюг: вимога → критерій прийняття → BDD-сценарій →
тікет → операція API → тест → код. Крок 11 цієї роботи вимагає ще двох ланок:
елемента інтерфейсу й розділу документації.

**Елемент інтерфейсу.** Окремої колонки не додано, бо в цій версії системи
інтерфейс — це і є REST API: саме операцію контракту бачить і викликає той,
хто системою користується. Колонку перейменовано з «API operation» на
«Елемент інтерфейсу» і на початку матриці пояснено, чому це те саме. Для
п'яти вимог рівня вебінтерфейсу, винесених за межі роботи, елемент названо
в розділі «Вимоги поза обсягом».

Це не формальність. Назвати операцію `POST /profiles` елементом інтерфейсу
чесно, а дописати неіснуючу кнопку, щоб колонка не була порожньою, —
навпаки.

**Розділ документації.** Додано окремою таблицею «Зв'язок вимог із
документацією»: розділ `docs/user-guide.md` і розділ API-довідника для
кожної вимоги. Дев'ята колонка в основній таблиці зробила б її нечитною —
вісім колонок уже на межі.

Для 11 вимог колонка документації користувача має прочерк, і це теж
рішення, а не пропуск: REQ-NF-001..REQ-NF-005, REQ-NF-009, REQ-NF-010 і
REQ-NF-015 стосуються процесу розробки або внутрішньої будови. Писати про
них у документації користувача не слід — вони лише відволікали б людину від
того, що вона може зробити.

## Навіщо автоматичний аудит

Матриця — це 64 рядки по вісім колонок. Прочитати її як текст неможливо:
очі ковзають, і рядок із порожньою коміркою посередині нічим не
відрізняється від заповненого. Саме тому крок 12 вимагає автоматичної
перевірки.

`tools/audit_traceability.py` шукає сім видів розривів:

| Вид | Що означає |
|---|---|
| вимога без рядка | ID оголошений у SRS, але в матриці його немає |
| рядок без вимоги | у матриці є ID, якого немає в специфікації |
| порожній зв'язок | вимога в обсязі роботи, але без тесту або без розділу документації |
| неіснуючий тест | названий файл тестів не існує |
| неіснуючий модуль | названий модуль коду не існує |
| неіснуюча операція | адреса API не оголошена в контракті |
| тест без вимоги | тест без позначки `@pytest.mark.requirement` |

## Перший прогін: 4 розриви

```
Вимог оголошено: 64
Рядків у матриці: 64
Тестів із позначкою вимоги: 157
Розривів: 4
```

Жодної неіснуючої назви: усі посилання на тести, модулі й операції вели
кудись. Усі чотири розриви виявилися одного роду — доказ є, але він не
автоматизований тест.

### Три вимоги, для яких тест не є доказом

| ID | Зміст | Чим доводиться |
|---|---|---|
| REQ-NF-002 | кожна функціональна вимога покрита тестом | інструментом `tools/requirement_coverage.py` |
| REQ-NF-013 | Python, FastAPI, SQLite | складом залежностей у `requirements.txt` |
| REQ-NF-015 | код у `/src`, тести в `/tests` | структурою каталогів |

Написати для них тест можна — наприклад, такий, що перевіряє існування
каталогу `/src`. Але це був би тест, який нічого не ловить: каталог не може
зникнути непомітно, бо без нього не запуститься жоден інший тест.

Тому в інструменті з'явився перелік `NO_TEST_EXPECTED` — вимога та причина,
чому доказом є не тест. Перелік короткий і явний навмисно: без нього
достатньо було б оголосити «тест тут не потрібен» де завгодно, і перевірка
перестала б щось означати. Причини друкуються у звіті, тому виняток лишається
на видноті, а не ховається в коді інструмента.

### Справжня знахідка: тест без вимоги

```
test_infrastructure.py::test_application_start_is_written_to_action_log
```

Цей тест перевіряє, що старт застосунку потрапляє до журналу дій
`logs/app.log`. Позначки вимоги в нього немає — і виявилося, що поставити
нíчого.

Журналювання всіх дій системи вимагає **завдання практикуму**: «ОБОВ'ЯЗКОВО
застосувати систему логування всіх дій в інформаційній системі». Але в
затвердженій SRS такої вимоги немає. Є REQ-NF-005 про журнал прогонів
тестів, REQ-NF-006 про журнал сесій агента, REQ-NF-008 про журнал помилок —
і жодної про журнал дій самої системи.

Тобто в системі є поведінка, яку не описує жодна затверджена вимога. За
правилами цього проєкту це саме те, проти чого він побудований: поведінка
поза специфікацією.

**Рішення.** Записано як відкрите питання **ВП-07**. Виправити це в ЛР6
неможливо: додавання вимоги до затвердженої SRS заднім числом зруйнувало б
сенс усіх попередніх контрольних точок, а адендум — це окремий цикл, а не
дія етапу документування. Тест лишається без позначки, а причина цього
записана в інструменті й друкується у звіті.

Показово, звідки взялася розбіжність. Вимога журналювання прийшла не з
SKED-діалогу й не зі специфікації, а з тексту завдання до ЛР5 — тобто ззовні
вже затвердженого ланцюга. Вона була виконана сумлінно, але не була
оформлена як вимога, і тому не потрапила ні в матрицю, ні в покриття. Знайшов
це не людина за два цикли роботи, а перший же прогін аудиту.

## Результат

```
python tools/audit_traceability.py
Вимог оголошено: 64
Рядків у матриці: 64
Тестів із позначкою вимоги: 157
Розривів: 0
```

Матриця повна: кожна оголошена вимога має рядок; кожен рядок посилається на
вимогу, що існує; кожен названий тест, модуль і операція існують; кожен тест
прив'язаний до вимоги, крім одного, чия причина записана.
