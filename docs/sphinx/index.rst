API-довідник системи обліку витрат на харчування
================================================

Технічний довідник для супроводу системи. Складається автоматично з
docstring-ів початкового коду, тому описує систему такою, якою вона
фактично є, а не такою, якою її задумували.

Версія 1.1.0 — базова специфікація ``spec/srs.tex`` плюс адендум
``spec/addendum-01-budgets.md``.

Інші документи проєкту:

* ``README.md`` — встановлення, запуск, конфігурація, тести;
* ``docs/user-guide.md`` — документація користувача: сценарії роботи
  через REST API;
* ``spec/api/openapi.yaml`` — затверджений контракт REST API;
* ``spec/glossary.md`` — глосарій предметної області;
* ``docs/coding-convention.md`` — конвенція оформлення коду;
* ``docs/docstring-tags.md`` — система теглів документації коду;
* ``spec/traceability.md`` — матриця простежуваності.

.. rubric:: Як читати довідник

Система поділена на шари, і розділи довідника йдуть у порядку від
зовнішнього шару до внутрішнього:

#. **Шар REST API** — маршрути, схеми запитів і відповідей, обробка
   помилок. Відповідає за адреси й коди статусів.
#. **Прикладні служби** — правила предметної області зі специфікації.
   Про HTTP не знають.
#. **Репозиторії** — доступ до бази. Про вимоги не знають.
#. **Обчислення** — гроші, періоди, підсумовування, перевірка даних.
   Чисті функції без стану й без бази.
#. **Інфраструктура** — налаштування, база даних, журналювання.

Межа між шарами однобічна: шар знає лише про той, що під ним. Маршрут не
торкається SQL, репозиторій не знає, яку вимогу він обслуговує.

.. rubric:: Посилання на вимоги

У docstring-ах стоять ID вимог у круглих дужках: ``(REQ-F-006)``,
``(ADD-01, REQ-A-001)``. Це замикає ланцюг простежуваності з боку коду:
матриця ``spec/traceability.md`` веде від вимоги до модуля, а ID у
docstring-у — назад, від рядка коду до вимоги, яка його зумовила.
