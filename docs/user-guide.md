# Документація користувача

Як користуватися системою обліку витрат на харчування: від створення
профілю до перегляду підсумків і бюджетів.

Поточна версія системи — серверна, без графічного інтерфейсу, тому робота
йде через запити REST API. Найпростіший спосіб — сторінка
`http://127.0.0.1:8080/docs`, яка відкривається після запуску сервера: на ній
перелічені всі операції, і кожну можна виконати прямо з браузера,
заповнивши поля.

Термінологія в цьому документі — за глосарієм `spec/glossary.md`. Як
запустити систему — в `README.md`.

## 1. З чого почати

### Створити профіль

Профіль — окремий простір обліку: власні покупки, категорії та бюджети.
Нічого з цього не видно з інших профілів. Один профіль — одна людина, або
одна мета обліку.

Без профілю додати покупку не можна, тому це перша дія в системі.

```
POST /profiles
{ "name": "Ілля" }
```

У відповіді — ідентифікатор профілю. **Збережіть його**: він входить до
адреси майже кожного наступного запиту.

```json
{ "id": "7f3c…", "name": "Ілля", "createdAt": "2026-11-16T18:30:00+02:00" }
```

Разом із профілем система одразу створює п'ять категорій: Продукти,
Ресторан, Доставка, Напої, Інше. Починати з порожнього переліку не
доводиться.

### Переглянути наявні профілі

```
GET /profiles
```

Якщо відповідь `{"items": []}` — профілів ще немає, почніть із попереднього
кроку.

## 2. Категорії

Категорія — ознака покупки, за якою групуються витрати. П'ять базових
категорій створюються з профілем; за потреби можна додати власні.

### Переглянути категорії

```
GET /profiles/{profileId}/categories
```

Біля кожної категорії є `purchaseCount` — скільки покупок до неї прив'язано.

### Додати власну категорію

```
POST /profiles/{profileId}/categories
{ "name": "Ринок" }
```

Назва має бути унікальною в межах профілю. У різних профілях категорії з
однаковою назвою — звичайна річ.

### Перейменувати категорію

```
PATCH /profiles/{profileId}/categories/{categoryId}
{ "name": "Базар" }
```

Покупки зберігають зв'язок із категорією: вони посилаються на неї за
ідентифікатором, а не за назвою.

### Видалити категорію

```
DELETE /profiles/{profileId}/categories/{categoryId}
```

Якщо категорія порожня — вона просто зникає.

Якщо в ній є покупки, система відмовить і повідомить, скільки саме покупок
до неї прив'язано. Це не помилка, а запитання: видаляючи категорію, ви
вирішуєте долю покупок у ній.

Щоб підтвердити, повторіть запит із параметром:

```
DELETE /profiles/{profileId}/categories/{categoryId}?confirm=true
```

Покупки **не зникнуть**: вони перейдуть до категорії «Інше», і лише потім
категорія видалиться. Загальна сума витрат не зміниться — зміниться лише
розбивка за категоріями.

Разом із категорією видаляється і бюджет, якщо він на неї був встановлений.

### Чому «Інше» не видаляється

Категорія «Інше» службова: саме до неї переходять покупки з видалених
категорій. Якби її можна було видалити, покупки з наступного видалення не
мали б куди подітися. Тому її не можна ані видалити, ані перейменувати.

## 3. Покупки

### Додати покупку

```
POST /profiles/{profileId}/purchases
{
  "name": "Кава",
  "categoryId": "a1b2…",
  "unitPrice": "80.00",
  "quantity": "2"
}
```

Що важливо знати:

* **Вартість не вказується.** Система рахує її сама як ціну за одиницю,
  помножену на кількість, і заокруглює до копійки. Передане значення
  вартості не береться.
* **Дата й час не вказуються.** Система проставляє поточний момент. Якщо
  покупка була раніше, дату можна змінити наступним запитом.
* **Ціна записується з двома знаками після коми:** `80.00`, а не `80`.
* **Кількість — до трьох знаків:** `0.7` для 700 грамів, `0.125` для 125.

Два записи з однаковими назвою, категорією та датою — це дві різні покупки,
а не помилка: дві однакові кави за день цілком можливі.

### Переглянути покупки

```
GET /profiles/{profileId}/purchases
```

Порядок — від новіших до старіших. За замовчуванням повертається 50 записів;
разом із ними приходить `total` — скільки всього записів у вибірці.

Вибірку можна звузити:

| Параметр | Що задає | Приклад |
|---|---|---|
| `from` | не раніше цієї дати, включно | `?from=2026-11-01` |
| `to` | не пізніше цієї дати, включно | `?to=2026-11-30` |
| `categoryId` | лише одна категорія | `?categoryId=a1b2…` |
| `limit` | скільки записів повернути | `?limit=100` |
| `offset` | скільки пропустити | `?offset=50` |

Наприклад, усі покупки за листопад:

```
GET /profiles/{profileId}/purchases?from=2026-11-01&to=2026-11-30
```

### Змінити покупку

```
PATCH /profiles/{profileId}/purchases/{purchaseId}
{ "unitPrice": "85.00" }
```

Надсилати треба лише ті поля, які змінюються. Решта лишається як була.

Змінити можна будь-що, зокрема дату й час — саме так до системи вносять
покупку, яку забули записати вчора:

```
PATCH /profiles/{profileId}/purchases/{purchaseId}
{ "occurredAt": "2026-11-15T19:30:00+02:00" }
```

Після зміни ціни або кількості вартість перераховується. Підсумки за
періоди теж змінюються — окремої дії для цього не потрібно.

### Видалити покупку

```
DELETE /profiles/{profileId}/purchases/{purchaseId}
```

Підсумки за періоди, яких покупка стосувалася, змінюються одразу.

## 4. Підсумки за періоди

Головне питання системи — «скільки пішло на їжу за цей час».

```
GET /profiles/{profileId}/summary?period=month
```

Параметр `period` набуває одного з чотирьох значень:

| Значення | Період | Межі |
|---|---|---|
| `day` | календарний день | доба цілком |
| `week` | календарний тиждень | з понеділка по неділю |
| `month` | календарний місяць | з 1-го по останнє число |
| `range` | довільний діапазон | від `from` до `to`, обидві дати входять |

Без інших параметрів береться період, у якому ми зараз: `period=week` — це
поточний тиждень.

Щоб порахувати за інший день, тиждень або місяць, додайте будь-яку дату
всередині потрібного періоду:

```
GET /profiles/{profileId}/summary?period=month&date=2026-10-15
```

Це підсумок за весь жовтень, а не за 15 жовтня: дата лише вказує, про який
місяць ідеться.

Довільний діапазон задається двома датами:

```
GET /profiles/{profileId}/summary?period=range&from=2026-11-01&to=2026-11-15
```

Обидві межі входять у період.

У відповіді — межі періоду, сума, валюта й кількість покупок:

```json
{
  "period": "month",
  "from": "2026-11-01",
  "to": "2026-11-30",
  "total": "4250.75",
  "currency": "UAH",
  "purchaseCount": 37
}
```

За період без покупок сума дорівнює `0.00`. Це не помилка, а відповідь: за
цей час витрат не було.

## 5. Розбивка за категоріями та графіки

### На що саме йдуть гроші

```
GET /profiles/{profileId}/summary/categories?period=month
```

Параметри періоду ті самі, що в підсумку. У відповіді — таблиця «категорія —
сума — частка у відсотках», упорядкована від найбільшої витрати:

```json
{
  "total": "4250.75",
  "items": [
    { "categoryName": "Продукти", "amount": "2100.00", "share": 49.4 },
    { "categoryName": "Ресторан", "amount": "1500.75", "share": 35.3 },
    { "categoryName": "Напої",    "amount":  "650.00", "share": 15.3 }
  ]
}
```

Категорії, у яких за цей період не було покупок, у таблицю не потрапляють.

### Витрати по днях місяця

```
GET /profiles/{profileId}/charts/daily?month=2026-11
```

Повертається по одному значенню на кожен день місяця — 28, 29, 30 або 31,
включно з днями, коли витрат не було. Такі дні мають значення `0.00` і
лишаються в ряду: саме провали в графіку показують, коли ви не витрачали.

### Витрати по місяцях року

```
GET /profiles/{profileId}/charts/monthly?year=2026
```

Дванадцять значень, з тієї самої причини.

Система повертає числа для графіка; малює графік той застосунок, що її
використовує.

## 6. Бюджети

Сума витрат сама по собі — просто число. Бюджет дає точку порівняння:
скільки ви збиралися витратити й скільки лишилося.

### Встановити бюджет

```
POST /profiles/{profileId}/budgets
{ "categoryId": "a1b2…", "limit": "3000.00" }
```

Бюджет місячний і діє для кожного календарного місяця. Категорія може мати
не більш ніж один бюджет.

### Переглянути бюджети

```
GET /profiles/{profileId}/budgets
```

За замовчуванням показники рахуються за поточний місяць. Для іншого місяця:

```
GET /profiles/{profileId}/budgets?month=2026-10
```

У відповіді по кожному бюджету:

```json
{
  "categoryName": "Продукти",
  "limit": "3000.00",
  "spent": "1200.00",
  "remaining": "1800.00",
  "exceeded": false,
  "exceededBy": "0.00"
}
```

Якщо витрати перевищили ліміт, `exceeded` стає `true`, `remaining` — `0.00`,
а `exceededBy` показує, на скільки саме перевищено:

```json
{
  "limit": "1000.00",
  "spent": "1200.00",
  "remaining": "0.00",
  "exceeded": true,
  "exceededBy": "200.00"
}
```

Витрати рахуються лише за вказаний місяць: покупка 1 листопада на показники
жовтня не впливає.

### Змінити або зняти бюджет

```
PATCH  /profiles/{profileId}/budgets/{budgetId}    { "limit": "2000.00" }
DELETE /profiles/{profileId}/budgets/{budgetId}
```

Після зміни суми залишок перераховується одразу. Видалення бюджету покупок
не чіпає: зникає лише порівняння, самі витрати лишаються на місці.

## 7. Вивантаження та резервна копія

### Вивантажити покупки у файл

```
GET /profiles/{profileId}/purchases/export?from=2026-11-01&to=2026-11-30
```

Повертається файл CSV із колонками: назва, категорія, ціна за одиницю,
кількість, вартість, дата й час. Без параметрів вивантажуються всі покупки
профілю.

> **Про Excel під Windows.** Файл записано в кодуванні UTF-8 без позначки
> BOM. Excel без цієї позначки показує українські назви нечитними
> («РљР°РІР°» замість «Кава»). Суми й дати при цьому правильні. Обхід:
> відкрити файл через «Дані → З тексту/CSV» і вибрати кодування UTF-8, або
> відкрити в LibreOffice чи Google Таблицях, де проблеми немає.
>
> Це відоме зауваження, зафіксоване як відкрите питання ВП-06. Додавання
> BOM змінює зовнішню поведінку операції, тому потребує окремого рішення, а
> не правки під час роботи.

### Зробити резервну копію

```
POST /backups
```

Створює копію файлу бази в каталозі резервних копій. У відповіді — ім'я
файла, розмір і час створення. Копія робиться засобом самої бази, тому
придатна для відновлення навіть якщо її зробили під час роботи системи.

## 8. Що робити, коли система відмовляє

Відповідь про відмову завжди має однакову будову:

```json
{
  "error": {
    "code": "CATEGORY_NOT_EMPTY",
    "message": "Категорія містить 12 покупки. Підтвердіть перенесення до категорії «Інше».",
    "requirement": "REQ-F-023",
    "details": [{ "field": "purchaseCount", "issue": "12" }]
  },
  "traceId": "3f1a…"
}
```

`message` — українською, для людини. `requirement` — номер вимоги, яку
порушено; за ним можна знайти правило в специфікації. `traceId` — номер
цього запиту в журналі: якщо звертаєтеся по допомогу, назвіть його.

Найчастіші відмови:

| Код | Що сталося | Що робити |
|---|---|---|
| `VALIDATION_FAILED` | дані не пройшли перевірку | подивіться `details` — там названо поле |
| `PROFILE_NOT_FOUND` | профілю з таким номером немає | перевірте `profileId` в адресі |
| `CATEGORY_NOT_FOUND` | категорії немає, або вона з іншого профілю | категорії одного профілю не видно з іншого |
| `PURCHASE_NOT_FOUND` | покупки немає, або вона з іншого профілю | те саме |
| `CATEGORY_NAME_TAKEN` | така назва категорії вже є в цьому профілі | оберіть іншу назву |
| `CATEGORY_NOT_EMPTY` | у категорії є покупки | повторіть запит із `?confirm=true` |
| `CATEGORY_IS_SYSTEM` | спроба змінити категорію «Інше» | її не можна ані видалити, ані перейменувати |
| `BUDGET_ALREADY_SET` | у категорії вже є бюджет | змініть наявний через `PATCH`, а не створюйте другий |
| `INVALID_PERIOD` | межі періоду задано неправильно | перевірте формат дат: `2026-11-01` |

### Часті непорозуміння

**«Ціна 100 не приймається».** Ціна записується з двома знаками після коми:
`100.00`. Зафіксовано як відкрите питання ВП-03 — зведення `100` до `100.00`
належить рівню інтерфейсу користувача, якого в цій версії немає.

**«Дата в майбутньому не приймається».** Облік фіксує те, що вже сталося.
Запис наперед означав би планування витрат, а це поза межами системи.

**«Видалив категорію — покупки зникли?»** Ні. Вони перейшли до категорії
«Інше». Загальна сума за період не змінилася — змінилася лише розбивка.

**«Підсумок за тиждень не збігається з очікуваним».** Тиждень рахується з
понеділка по неділю. Якщо ви рахували з неділі, різниця буде саме на один
день.
