# Coding Convention проєкту «Облік витрат на харчування»

Крок 1 лабораторної роботи №6. Документ фіксує узгоджений стиль оформлення
програмного коду. Машинне втілення конвенції — файл `ruff.toml` у корені
репозиторію; кожне налаштування в ньому має відповідний пункт тут.

Версія конвенції: 1.0. Прийнято: 16.11.2026, Майстренко Ілля, група КН-32.

## 1. Основа

За основу взято офіційні документи мови, а не власний набір правил:

| Документ | Що визначає |
|---|---|
| PEP 8 | відступи, пробіли, довжина рядка, порядок імпортів, іменування |
| PEP 257 | призначення й оформлення docstring-ів |
| PEP 484, PEP 604 | анотації типів, запис `X \| None` замість `Optional[X]` |
| Google Python Style Guide, розділ 3.8 | структура docstring-а: секції `Args`, `Returns`, `Raises` |

Підстава для вибору: проєкт написано на Python 3.13, і для цієї мови існує
усталений офіційний стиль. Власна конвенція вводиться лише там, де офіційні
документи не дають відповіді або де затверджений контракт API вимагає
іншого — усі такі місця перелічені в розділі 6.

## 2. Інструмент перевірки

Відповідність перевіряє `ruff` версії 0.16 і новішої — він поєднує
`pycodestyle`, `pyflakes`, `isort`, `pep8-naming` і `pydocstyle` в одному
проході, тому конвенція перевіряється однією командою:

```
ruff check .          # аналіз відповідності
ruff format --diff .  # які саме рядки переформатував би форматувальник
```

Увімкнені набори правил: `E`, `W` (PEP 8), `F` (невикористане й невизначене),
`I` (порядок імпортів), `N` (іменування), `D` (docstring-и, конвенція
`google`), `UP` (застарілі конструкції), `B` (типові пастки), `C4`, `SIM`,
`RET`, `PTH` (шляхи через `pathlib`), `RUF`.

## 3. Оформлення

| Правило | Значення | Примітка |
|---|---|---|
| Довжина рядка | 100 **символів** | не байтів: кириличний текст у байтах удвічі довший, і підрахунок у байтах дає хибні зауваження |
| Відступ | 4 пробіли | табуляція не використовується |
| Лапки | подвійні | `"` для рядків і docstring-ів |
| Кінець рядка | LF | у репозиторії; Git на Windows переносить на CRLF у робочій копії |
| Порожній рядок після docstring-а функції | не ставиться | правило D202 |
| Кодування | UTF-8 без BOM | тексти повідомлень українською зберігаються в коді як є |

Імпорти: три групи — стандартна бібліотека, зовнішні пакети, модулі проєкту;
`food_expenses` вважається модулем проєкту. Усередині пакета
використовуються відносні імпорти (`from ..models import Profile`), між
пакетами — абсолютні.

На початку кожного модуля стоїть `from __future__ import annotations`:
анотації залишаються рядками, тому циклічні залежності між шарами не
виникають навіть у підказках типів.

## 4. Іменування

| Сутність | Форма | Приклад |
|---|---|---|
| Модуль, пакет | `lower_snake_case` | `logging_setup.py` |
| Клас | `CapWords` | `PurchaseRepository` |
| Функція, метод, змінна | `lower_snake_case` | `calculate_amount` |
| Стала | `UPPER_SNAKE_CASE` | `CENT`, `BASE_CATEGORY_NAMES` |
| Внутрішній елемент | з підкресленням на початку | `_to_profile` |

Імена сутностей предметної області беруться з глосарію `docs/glossary.md`, а
не придумуються заново. Зв'язок «термін специфікації — ім'я в коді»
перевіряється окремо (крок 3, журнал `logs/glossary-audit.md`).

## 5. Docstring-и

Обов'язкові для публічного модуля, класу, функції й методу. Мова — українська,
як і вся інша документація проєкту: терміни мають збігатися з глосарієм і
текстом SRS.

Формат — Google-style. Перелік застосованих теглів, їхнє значення і приклади
подані окремим документом `docs/docstring-tags.md`.

Docstring фіксує призначення, параметри, результат, істотні обмеження та
посилання на ID вимоги, яку елемент реалізує. Він не переповідає очевидний
код: рядок «повертає список покупок» над методом `list_all` інформації не
додає, а от «порядок: новіші зверху (REQ-F-019)» — додає.

## 6. Усвідомлені відхилення

Відхилення нижче прийняті свідомо; кожне вимкнене в `ruff.toml` разом з
обґрунтуванням, а не замовчується.

| Правило | Де | Чому відхилення прийнято |
|---|---|---|
| `N818` (клас-виняток має закінчуватися на `Error`) | `errors.py`, 12 класів | ім'я класу дослівно відповідає коду помилки затвердженого контракту: `ProfileNotFound` ↔ `PROFILE_NOT_FOUND`. Суфікс `Error` розірвав би цей зв'язок, а він — єдина гарантія, що код помилки в відповіді й клас у коді не розійдуться |
| `N815` (змінна класу в mixedCase) | `api/schemas.py`, 6 полів | імена полів `unitPrice`, `occurredAt`, `categoryId` задані схемами OpenAPI, затвердженими на API-GATE. Перейменування змінило б зовнішній інтерфейс |
| `N802` (ім'я функції в нижньому регістрі) | `logging_setup.py`, `formatTime` | метод перевизначає `logging.Formatter.formatTime` стандартної бібліотеки; ім'я задане нею |
| `B008` (виклик функції у значенні параметра за замовчуванням) | `api/params.py`, `api/dependencies.py`, маршрути | `Depends()`, `Path()`, `Query()` у значенні за замовчуванням — спосіб оголошення залежностей, передбачений самим FastAPI |
| `D100`–`D104` для тестів | `tests/` | тест описує себе іменем і маркером `@pytest.mark.requirement`; docstring дублював би ім'я |
| `D203`, `D213` | усюди | правила суперечать `D211` і `D212`; обрано варіант без порожнього рядка перед описом і з описом у першому рядку |
| `RUF001`–`RUF003` | усюди | правила попереджають про кириличні літери, схожі на латинські; у проєкті з українськими текстами це шум |

## 7. Автоматичне переформатування

`ruff format` застосовується, але з обмеженням: тільки там, де зміна
стосується виключно пробілів, переносів і лапок. Після будь-якого
переформатування обов'язково прогоняються повний набір тестів і перевірка
контракту — доказ, що зовнішня поведінка не змінилася, фіксується в
`logs/convention-audit.md`.

Перейменування, зміна сигнатур і будь-яка правка, що торкається імен в API,
автоматичному інструменту не доручається.

## 8. Межі конвенції

Конвенція стосується коду в `src/`, `tests/` і `tools/`. Згенеровані файли
(`docs/sphinx/_build/`, `.ruff_cache/`, `.pytest_cache/`) під неї не
потрапляють і перелічені в `.gitignore`.
